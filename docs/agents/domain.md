# Domain docs

## Layout

This is a single-context project. Shared domain terms live in root `GLOSSARY.md`; architectural decisions live in `docs/adr/`.

## Read before exploring

Read the glossary and ADRs relevant to the area being explored or changed. If they do not exist, proceed silently. Create domain documents lazily when terminology or decisions are resolved through domain modeling.

## Consumer rules

Use glossary terms consistently in tickets, code, tests, and proposals. When an important concept lacks a definition, note the gap for domain modeling.

Surface conflicts with an existing ADR explicitly, identifying the ADR and the reason to revisit it. Preserve established decisions until a replacement is agreed.
